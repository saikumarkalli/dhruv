# Phase 1 Data Model: Money Tab (Phase 3)

Maps `spec.md`'s Key Entities to concrete storage. Everything new lands in the **`finance` Postgres
schema** (ADR-0033), authored as declarative per-object files under
`supabase/schemas/finance/` with the migration generated by `supabase db diff` (ADR-0032) — grants
hand-added, since `db diff` cannot express them.

RLS on every table: `user_id = auth.uid()` directly, or transitively through the owning row. No
`anon` grant anywhere — every tracker call is authenticated (ADR-0029).

## Existing entities referenced, not changed

`finance.holdings`, `finance.valuations`, `public.liabilities_meta` (Phase 1/2) are untouched by
this phase except that `liabilities_meta.linked_account_id` — deliberately left null in Phase 2
because no `accounts` table existed — becomes writable now.

> **Carried-over correction to check when this lands**: Phase 2's `data-model.md` names the table
> `public.liabilities_meta`, while ADR-0033 moved the tracker's tables into the `finance` schema.
> If Phase 2 ships it in `public`, this phase's foreign key must qualify accordingly (or Phase 2's
> table moves with the same `ALTER TABLE … SET SCHEMA` pattern ADR-0033 already used). Flagged, not
> silently assumed either way.

## New tables

### Account → `finance.accounts`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `user_id` | uuid, FK → `auth.users` | RLS subject |
| `name` | text, not null | |
| `type` | text, not null | `BANK \| CASH \| WALLET \| CREDIT_CARD` — TEXT, append-only constants (Article IX) |
| `mask` | text, nullable | last 4 digits only; never a full account number |
| `is_primary` | boolean, default false | at most one true per user — partial unique index |
| `limit_paise` | bigint, nullable | credit accounts only |
| `due_day` | integer, nullable | day-of-month; feeds Home's UPCOMING card-bill row (FR-034) |
| `opening_balance_paise` | bigint, not null, default 0 | the only stored balance — current balance is derived (see `v_account_balances`) |
| `reconciled_at` | timestamptz, nullable | drives the staleness flag (FR-020); null = never reconciled |
| `created_at` | timestamptz, default now() | |
| `deleted_at` | timestamptz, nullable | soft delete |

RLS: SELECT/INSERT/UPDATE own rows. No client DELETE (erasure via `delete_my_data()`).

**Validation** (repository boundary): `type` enum-validated; `limit_paise`/`due_day` only accepted
for `CREDIT_CARD`; an account may not be soft-deleted while non-deleted transactions reference it
until the user has been told what happens to them (spec Edge Cases).

### Transaction → `finance.transactions`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `user_id` | uuid, FK → `auth.users` | |
| `type` | text, not null | `EXPENSE \| INCOME \| TRANSFER` (BR-D1) |
| `amount_paise` | bigint, not null, `CHECK > 0` | **Article VII** — sign comes from `type`, never from the stored value |
| `account_id` | uuid, not null, FK → `accounts` | source account |
| `to_account_id` | uuid, nullable, FK → `accounts` | destination — TRANSFER only |
| `category_id` | uuid, nullable, FK → `categories` | required for EXPENSE/INCOME, null for TRANSFER |
| `payee` | text, nullable | |
| `note` | text, nullable | |
| `occurred_at` | timestamptz, not null | the date the ledger groups by — not `created_at` |
| `cleared` | boolean, default true | D4's cleared state |
| `receipt_path` | text, nullable | **device-local URI** this phase (research R6) |
| `goal_id` | uuid, nullable | forward-compatible; `goals` arrives Phase 4, so no FK yet |
| `recurring_id` | uuid, nullable, FK → `recurring_templates` | set when accepted from a recurring suggestion |
| `split_group_id` | uuid, nullable | parts of one split share this id; see Splits below |
| `source` | text, not null, default `MANUAL` | `MANUAL \| RECURRING \| RECONCILE \| SMS \| IMPORT` (last two unused until Phase 7) |
| `created_at` / `deleted_at` | timestamptz | soft delete keeps the audit trail intact |

RLS: SELECT/INSERT/UPDATE own rows; no client DELETE.

**Constraints (DB-level, not just repository)**:
- `TRANSFER` ⇒ `to_account_id` not null, `to_account_id <> account_id`, `category_id` null.
- `EXPENSE`/`INCOME` ⇒ `to_account_id` null, `category_id` not null.

**Indexes**: `(user_id, occurred_at DESC)` for the ledger; `(account_id)`, `(to_account_id)`,
`(category_id)`, `(split_group_id)`, `(recurring_id)`.

**Splits** (FR-004) are **sibling rows sharing `split_group_id`**, each with its own category and
amount — there is no parent row holding a total. Consequence: nothing can double-count, every view
already sums the parts correctly with no change, the audit trigger covers each part, and "the parts
sum to the whole" needs no constraint because the whole is defined as the sum. A non-split
transaction has `split_group_id = null`.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `transaction_id` | uuid, FK → `transactions` | ownership transitive — no `user_id` column, same pattern as `valuations` |

## Views (server-side aggregation — NFR-8)

### `finance.v_account_balances`
Per account: `opening_balance_paise` + Σ signed transactions (INCOME `+`, EXPENSE `−`, TRANSFER `−`
on `account_id` and `+` on `to_account_id`), excluding soft-deleted rows. Also carries `type` and a
`counts_as_spendable` flag (`type IN ('BANK','CASH','WALLET')`), so "spendable now" (FR-017,
`MNY-BR-002`) is a filtered sum of a handful of rows rather than a rule the client re-derives.
Credit accounts therefore land **negative** naturally (BR-D2) — no special case.

### `finance.v_month_summary`
Per user per month: `income_paise`, `expense_paise`, `excluded_paise`, `transfer_paise`.
`expense_paise` **excludes** `TRANSFER` rows (BR-D1) and rows in `excluded_from_spend` categories
(FR-025); `excluded_paise` keeps that money visible so D1's saved-percentage arithmetic is
explainable rather than mysteriously short. Backs D1's pinned summary (FR-011).

### `finance.v_category_spend`
Per user, month and category: total and share of that month's spend. Same two exclusions as above.
Backs D8's per-row spend/share (FR-022) and, from Phase 4, budget consumption.

## Functions and trigger

### `finance.fn_transaction_audit()` + trigger `trg_transaction_audit`
`AFTER INSERT OR UPDATE OR DELETE ON finance.transactions FOR EACH ROW` — appends the matching
`transaction_events` row (`CREATED` / `EDITED` / `CATEGORY_CHANGED` when `category_id` changed /
`DELETED` when `deleted_at` transitions from null). Makes BR-D5 / `MNY-BR-006` structural
(research R4).

### `finance.merge_categories(p_source uuid, p_target uuid) returns integer`
Re-points every non-deleted transaction from source to target, soft-deletes the source category,
returns the count moved. Invoker rights — RLS keeps it to the caller's own rows. Atomic, so a
half-finished merge cannot exist (research R9, `MNY-BR-004`).

### `public.delete_my_data()` — extended
Gains DELETEs for `transaction_events`, `transactions`, `suggestions`, `recurring_templates`,
`categories`, `accounts`, in FK-safe order, alongside the holdings/valuations it already removes
(ADR-0029 §5). Without this extension the 7-day erasure guarantee (NFR-1) would silently miss every
row this phase introduces.

## State transitions

- **Transaction**: created → (edited | re-categorised)* → soft-deleted. Every arrow writes an event
  row. Never hard-deleted by a client; hard removal only through `delete_my_data()`.
- **Pending entry**: `PENDING` → `ACCEPTED` (writes a `transactions` row with
  `source = 'RECURRING'` and an `ACCEPTED_FROM_RECURRING` event) or `IGNORED` (writes nothing).
  Terminal either way — a pending entry is never re-opened (FR-029).
- **Recurring definition**: active ⇄ paused (`paused`/`paused_at`); a paused definition produces no
  occurrences (FR-031). Deleting one soft-deletes it and leaves already-accepted transactions alone.
- **Account**: created → reconciled* (each reconciliation sets `reconciled_at`, and writes an
  adjustment transaction when the stated balance differs — research R8) → soft-deleted.
- **Category**: created → renamed* (identity unchanged, FR-023) → merged away (soft-deleted, its
  transactions re-pointed, FR-024) or soft-deleted directly.
