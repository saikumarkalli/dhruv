# Quickstart: Validate Plan Live Modules (Phase 4)

Validation guide only — implementation detail lives in `tasks.md` (generated by `/speckit-tasks`)
and the feature's own source. Entities: [data-model.md](data-model.md). Routes:
[contracts/routes.md](contracts/routes.md). Decisions: [research.md](research.md).

## Prerequisites

- Phases 1–3 shipped: signed in via Google, "Sync my financial records" consent on, net worth
  working (holdings, valuations, `liabilities_meta`, `v_latest_valuation`), and the Money tab
  recording transactions against categories (`v_category_spend`, `v_month_summary`).
- `:libs:core` carries the components this phase consumes but does not build: `NxTextField` error +
  helper state and `NxButton` sizes/loading (Phase 2), `StatusBadge` and `InfoBanner` (Phase 3's
  batch B7), `SelectionSheet` and `NxSelect`.
- This phase's migration applied to `dhruv-dev` — six tables, three views, the earmark-guard trigger,
  and the extended `delete_my_data()` (see `data-model.md`). Authored declaratively under
  `supabase/schemas/finance/`, migration generated by `supabase db diff -f plan_phase4`, grants
  hand-added (ADR-0032).
- `:apps:finance:feature:planning`, `:insurance` and `:retirement` registered in
  `settings.gradle.kts` (each with its `projectDir` remap under `apps/finance/feature/plan/`) and
  wired into `CalculatorApplication`'s Koin graph.
- The five new flags present in `platform/feature-flags/dhruv-finance.json`.

## Automated validation

```powershell
# Full gate: all unit tests + ArchUnit + merged JaCoCo + coverage floor
./gradlew regressionCheck

# The four engines alone — pure JVM, no Android, milliseconds; run these while iterating
./gradlew :apps:finance:data:testDebugUnitTest --tests "com.dhruv.finance.data.planning.*"

# This feature's three modules
./gradlew :apps:finance:feature:planning:testDebugUnitTest
./gradlew :apps:finance:feature:insurance:testDebugUnitTest
./gradlew :apps:finance:feature:retirement:testDebugUnitTest

# Money-precision guard — must stay green with the engines OUTSIDE tracker/ (research R2)
./gradlew checkTrackerMoneyPrecision

# Schema docs + declarative/migration equivalence (ADR-0032/0033 guards)
python scripts/db/gen_schema_docs.py equiv
python scripts/db/gen_schema_docs.py docs --check
```

`checkTrackerMoneyPrecision` deserves a deliberate look on this phase, not just a green tick. It is
the guard research R2 exists to protect. If it fails on a retirement or payoff file, the fix is to
move that file back out of `tracker/` — **not** to relax the task's regex, and not to rewrite the
engine to avoid the word `Double`.

## Coverage validation

```powershell
# Merged report + floor check (both are part of regressionCheck above; run alone to iterate)
./gradlew jacocoAggregatedReport jacocoCoverageVerification

# Human-readable per-module numbers (same parser CI uses for the Job Summary / PR comment)
python scripts/ci/regression_summary.py
```

Read the HTML at `build/reports/jacoco/jacocoAggregatedReport/jacocoAggregatedReport.html`; the XML
beside it is what the parser and the floor check consume.

Four things to confirm, in order:

1. **All three modules are measured at all.** `:apps:finance:feature:planning`, `:insurance` and
   `:retirement` each appear as their own row. If one shows under `(other)`, `_FEATURES` in
   `scripts/ci/regression_summary.py` is missing it; if it is absent from the HTML report entirely,
   `coveredModules` in the root `build.gradle.kts` is missing the module path. Either way the gate is
   passing vacuously for that module's code. Six registrations, three modules — check all six.
2. **The engines' own coverage is high, and separately visible.** They live in `:apps:finance:data`
   under `planning/`, are pure functions, and have no excuse to sit below the module average. If
   `BudgetPaceEngine`/`DebtPayoffEngine`/`RetirementProjectionEngine`/`InsuranceCoverEngine` are not
   near-fully covered, the golden-value fixtures are thinner than `RET-BR-001` and `PLN-BR-004` ask
   for.
3. **Merged line coverage rose**, and `globalLineFloor` is ratcheted to just under the new measured
   figure — never above it (Article X / ADR-0013: a non-regression ratchet, not a target). This phase
   should raise it more than a typical screen phase does, because the engines are exactly the shape
   the JVM gate sees completely.
4. **Both numbers are recorded**, not one. A feature module's own percentage is dragged down by
   Compose screen files the JVM gate never executes; record the module total and the engine/ViewModel
   logic total side by side in the QA catalog's §13 summary.

Expected: all green. Every test cites a `PLN-*`, `INS-*` or `RET-*` scenario ID from
`apps/finance/docs/superpowers/specs/2026-08-09-qa-test-scenario-catalog.md` §5–§7 — a test with no
citation is a review-blocking finding (constitution Article I).

After the migration lands, regenerate the web types so the parallel web track stays typed:

```powershell
supabase gen types typescript --schema public,finance > web/src/shared/types/database.ts
```

## Manual end-to-end scenarios (mirror spec.md's Acceptance Scenarios)

1. **Story 1 — pace is stated, not implied** (`PLN-BR-002`, `PLN-UI-001`, `PLN-UI-002`)
   With a month of transactions and budgets set, open Plan → Budgets on a known day. Compute
   `elapsed = day / days_in_month` and `used = spent / budget` by hand for one category. Expect: the
   pace sentence's percentage matches, the category's bar sits ahead of the month marker if and only
   if `used > elapsed`, and the overview shows percentage used, amount left, total and days
   remaining.

2. **Story 1 — exclusions hold** (`PLN-BR-003`, FR-010)
   Record a transfer between two of your own accounts, and a transaction in a category marked
   excluded from spend. Expect: neither moves any budget figure by a single paisa. This is the
   property that must come from `v_category_spend`, not from Kotlin — if it holds on screen but the
   view returns the transfer, the exclusion is implemented in the wrong place.

3. **Story 2 — recovery insight is reproducible and labelled** (`PLN-UI-003`, `PLN-BR-005`)
   Open an over-budget category's detail. Expect: the stated average and projected overage recompute
   from that category's own recent transactions, the overage is stated in words and money with days
   left, and the insight carries a visible derived-insight marker. Then use "Raise budget" and
   confirm every derived figure on the screen updates, and "Alert me at 80%" and confirm the
   threshold shows as set after leaving and returning.

4. **Story 2 — the deferred leg** (`PLN-FLOW-003`, research R8)
   The notification-initiated half of this flow cannot be exercised until Phase 6 ships screen B2.
   Verify the chain from the budget detail onward, then record the row as **deferred with the R8
   reason cited** — not as passed, and not as silently unticked. A row left blank at the checkpoint
   fails the gate; a row deferred with a stated reason does not.

5. **Story 3 — linking moves nothing** (`PLN-BR-001`, `PLN-FLOW-002`, FR-018)
   Create a goal, link one holding whole and another at a partial earmark. Expect: progress equals
   the sum of the whole holding's current value and the earmarked fraction of the second. Then check
   what did *not* happen — no transaction was written, no holding's own value changed. Assert this
   at the repository level, not by eyeballing the ledger; "no write occurred" is the assertion both
   catalog rows actually demand.

6. **Story 3 — the earmark cap is enforced in the database** (FR-024)
   Earmark 70% of one holding to goal A, then attempt 40% of the same holding to goal B. Expect: a
   readable refusal, not a silent acceptance. Then repeat the second write directly against
   PostgREST, bypassing the app. It must still be refused — that is the trigger doing its job, and
   the client-side check alone would have let it through under a race.

7. **Story 3 — unfunded is not zero** (`PLN-UI-004`, FR-020)
   Set up three goals: one on track, one short of its target date, one with nothing linked. Expect
   three distinct status texts, and specifically that the unlinked goal says no funding is linked
   rather than showing 0% progress.

8. **Story 3 — the earmark renders as a fraction** (`PLN-UI-005`, research R1)
   Open the partially-earmarked goal's detail. Expect "funded by" to show the earmark as a
   percentage and its rupee value, reflecting the fraction and not the holding's full value. The
   design's "56 g" quantity form is **not** expected — holdings carry no quantity yet, and R1 records
   why this is a deliberate narrowing rather than a defect.

9. **Story 4 — ordering and trade-off** (`PLN-BR-004`, `PLN-UI-006`)
   With at least three debts of differing rate and balance, toggle both strategies. Expect:
   highest-interest-first orders by rate descending, smallest-balance-first by balance ascending,
   both stable across reopenings, and the "N months slower, ₹X more interest" sentence consistent
   with both projections and carrying a derived-insight marker. Change the extra-per-month amount and
   confirm the debt-free date, interest saved and months saved all move together.

10. **Story 4 — the debt that does not clear** (FR-031, research R9)
    Enter a debt whose minimum payment is at or below its monthly interest. Expect: the screen names
    it as not clearing under the current plan, within a normal render time. A hang means the month
    cap is missing; a silently absent debt means the cap exists but the statement does not.

11. **Story 5 — renewal window and gaps** (`INS-UI-001`, `INS-UI-002`)
    Record one policy renewing inside the window and one outside. Expect: a banner for the first
    only, with correct days remaining and the lapse consequence stated. Remove cover for one risk
    category and confirm the gaps section names that specific category, not a generic warning.

12. **Story 5 — rule of thumb and its basis** (`INS-BR-001`, research R3)
    Expect life cover compared against ten times annual income plus outstanding loans, with the
    formula visible and the shortfall named. Then check the honesty case: with fewer than twelve
    months of ledger, the screen must say what it could not compute from, rather than annualising a
    partial year silently.

13. **Story 5 — marking a premium paid** (`INS-FLOW-001`, FR-039)
    Mark a due premium paid. Expect: a row appended to the premiums history and that policy's renewal
    banner cleared. Then confirm the append-only property directly — attempting to update or delete
    that premium row through PostgREST must be refused, because no such policy exists on the table.

14. **Story 6 — assumptions on the same screen** (`RET-UI-002`, BR-E4)
    Open Retirement. Expect all five assumptions readable without navigating away from the projected
    corpus. A drill-in to edit them fails this row even if the values are correct.

15. **Story 6 — scenarios are distinct, and each assumption moves the right way** (`RET-UI-001`,
    `RET-BR-001`)
    Toggle base, optimistic and cautious: expect three different corpus figures. Then vary one
    assumption at a time against the golden fixtures and confirm each moves the corpus in its
    expected direction. Also try the contradictory inputs — retire-at age below current age, life
    expectancy below retirement age, inflation above both returns — and confirm each produces a
    stated result rather than a blank chart or a negative corpus presented as fact.

16. **Story 6 — the scenario persists, the projection does not** (`RET-FLOW-001`, FR-049)
    Set non-default assumptions, save the scenario, leave and return. Expect the assumption values
    to reappear. Then confirm what is *not* stored: no corpus figure is persisted anywhere — the
    projection is recomputed, so editing an assumption can never leave a stale number behind.

17. **Story 7 — Plan leads with planning** (`PLN-FLOW-001`, ADR-0027)
    Open the Plan tab. Expect live modules first (this month: budgets, goals; long run: debt payoff,
    insurance, retirement) with the four calculators as a strip below. Open each row and confirm the
    Plan tab stays selected with one back path. Turn one module's flag off and confirm only that row
    degrades — the tab and the calculators keep working.

18. **Cross-cutting — every derived statement is labelled** (FR-047, `PLN-BR-005`)
    Walk E3, E4, E5, E6 and E9 and confirm every computed sentence carries the marker. This is the
    one requirement in the feature that is satisfied four times and missed once; research R5 routes
    them all through `SmartInsightCard` so a single assertion covers all five screens.

19. **Cross-cutting — designed states, not spinners** (FR-048, NFR-4)
    On each of the nine screens: sign out, then re-enter; enable airplane mode with nothing cached;
    force a failed load. Expect the signed-out, offline and error cards each time — never a blank
    screen and never a spinner that does not resolve. On E4 specifically, confirm "no goals at all"
    (empty state) and "a goal with nothing linked" (goal state) render differently.

20. **Cross-cutting — erasure covers the new tables** (NFR-1, ADR-0029 §5)
    With budgets, goals, links, policies, premiums and a saved scenario in place, run Settings →
    Privacy → "Delete my data". Expect every row across all six tables gone, and the Plan tab back to
    its empty states rather than to an error.

## Definition of done for this quickstart

- `./gradlew regressionCheck` green, including `checkTrackerMoneyPrecision` with the engines outside
  `tracker/`.
- Both schema guards (`equiv`, `docs --check`) green; `supabase/SCHEMA.md` regenerated.
- All three modules visible as their own rows in the coverage summary; floor ratcheted once, to the
  measured value.
- All 21 catalog rows (`PLN-*` 13, `INS-*` 4, `RET-*` 4) either closed or explicitly deferred with a
  stated reason — `PLN-FLOW-003` is the known deferral, citing research R8.
- The five deltas this feature makes to the design-v1 implementation plan (research R1, R2, R3, R4,
  R9) written back into that plan's Phase 4 section as a dated note.
