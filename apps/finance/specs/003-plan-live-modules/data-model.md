# Phase 1 Data Model: Plan Live Modules (Phase 4)

Maps `spec.md`'s Key Entities to concrete storage. Everything new lands in the **`finance` Postgres
schema** (ADR-0033), authored as declarative per-object files under `supabase/schemas/finance/` with
the migration generated by `supabase db diff` (ADR-0032) — grants hand-added, since `db diff` cannot
express them.

RLS on every table: `user_id = auth.uid()` directly, or transitively through the owning row. No
`anon` grant anywhere — every tracker call is authenticated (ADR-0029).

Money is `bigint` paise everywhere (Article VII). Rates and shares are integers — basis points or
whole percent — never `numeric` and never `Double`.

## New tables

### Budget → `finance.budgets`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `user_id` | uuid, FK → `auth.users` | RLS subject |
| `category_id` | uuid, FK → `finance.categories` | one budget per category per period |
| `period_month` | date, not null | first day of the calendar month; the period *is* the month (BR-E2, FR-005) |
| `amount_paise` | bigint, not null | raising a budget (FR-013) updates this row for the current period only |
| `alert_pct` | integer, nullable | FR-014; written this phase, consumed in Phase 6 (research R8) |
| `created_at` | timestamptz, default now() | |
| `deleted_at` | timestamptz, nullable | soft delete |

Unique index on `(user_id, category_id, period_month) where deleted_at is null`.

RLS: SELECT/INSERT/UPDATE own rows. No client DELETE (erasure via `delete_my_data()`).

**Validation** (repository boundary): `amount_paise > 0`; `alert_pct` in 1–100; `period_month` must
be the first of a month; a budget may not be created against a category with
`excluded_from_spend = true` (BR-E3, FR-010) — that combination has no meaning and would render as a
budget permanently at 0%.

### Goal → `finance.goals`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `user_id` | uuid, FK → `auth.users` | |
| `name` | text, not null | |
| `target_paise` | bigint, not null | |
| `target_date` | date, not null | drives the on-track / needs-per-month status (FR-020) |
| `icon` | text, nullable | icon key, not a drawable reference |
| `created_at` / `deleted_at` | timestamptz | soft delete |

RLS: SELECT/INSERT/UPDATE own rows.

**The table stores no progress and no saved amount.** Progress is entirely derived from
`v_goal_progress` (BR-E1, FR-017). A `saved_paise` column was deliberately not added: it would be a
cached copy of a live figure, and the first time a holding's valuation changed without the cache
being refreshed, the goal would claim money the user does not have.

### Goal funding link → `finance.goal_links`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `goal_id` | uuid, FK → `finance.goals` | ownership is transitive through the goal — no `user_id` of its own |
| `holding_id` | uuid, FK → `finance.holdings` | |
| `earmark_bps` | integer, not null | 1–10000; **10000 = the whole holding** (research R1) |
| `created_at` / `deleted_at` | timestamptz | unlinking is a soft delete |

Unique index on `(goal_id, holding_id) where deleted_at is null` — a goal links a holding once, at
one earmark, rather than accumulating rows.

RLS: SELECT/INSERT/UPDATE/DELETE where the parent goal's `user_id = auth.uid()`. DELETE is permitted
here (unlike other tables) because a link is a user's own annotation, not a financial record — it
carries no money and its removal loses no history.

**Validation**: `earmark_bps between 1 and 10000`, as a table CHECK. The **cross-row** rule — the sum
of live `earmark_bps` for one holding across all of a user's goals may not exceed 10000 (FR-024) — is
a CHECK constraint's blind spot and is enforced by a trigger instead (see below).

**Creating or removing a link writes nothing else.** No transaction, no valuation, no change to the
holding (FR-018, BR-E1). This is asserted at the repository level, not left to reviewer memory
(`PLN-BR-001`, `PLN-FLOW-002` both demand it explicitly).

### Premium payment → `finance.policy_premiums`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `policy_id` | uuid, FK → `finance.policies` | ownership transitive through the policy |
| `paid_on` | date, not null | |
| `amount_paise` | bigint, not null | |
| `created_at` | timestamptz, default now() | |

RLS: **SELECT + INSERT only — no UPDATE, no DELETE policy at all.** Same shape as `valuations`
(ADR-0029 §4): the table is append-only at the database layer, not by client convention (Article IX).
A premium recorded in error is corrected by appending, never by rewriting — and because there is no
UPDATE policy, no future code path can quietly do otherwise.

There is deliberately no `deleted_at`: a soft-delete column on an append-only table is an invitation
to treat it as mutable.

### Retirement scenario → `finance.retirement_scenarios`

| Column | Type | Notes |
|---|---|---|
| `id` | uuid, PK | |
| `user_id` | uuid, FK → `auth.users` | |
| `name` | text, not null | |
| `kind` | text, not null | `BASE \| OPTIMISTIC \| CAUTIOUS \| CUSTOM` — append-only constants |
| `assumptions` | jsonb, not null | the five inputs; see below |
| `created_at` / `deleted_at` | timestamptz | soft delete |

`assumptions` shape — validated at the repository boundary, not by the database:

```json
{
  "retire_at_age": 60,
  "monthly_spend_today_paise": 8500000,
  "inflation_bps": 600,
  "pre_return_bps": 1100,
  "post_return_bps": 700,
  "life_expectancy": 85
}
```

**No projected corpus is stored.** The projection is derived on read from these six values
(FR-049) — storing it would put a derived figure next to recorded facts, where a later reader would
have no way to tell that it was computed under assumptions that have since been edited. `RET-FLOW-001`
asks only that the **assumptions** reappear, which is exactly what this table promises.

`monthly_spend_today_paise` is seeded from `v_annual_income` (research R3) and then owned by the
scenario; the other five have no derived source and are pure user inputs.

## Views (server-side aggregation — NFR-8)

### `finance.v_budget_status`

`budget_id · user_id · category_id · period_month · amount_paise · spent_paise · category_name ·
excluded_from_spend`

Joins `budgets` to Phase 3's `v_category_spend` for the same month. Two correctness properties come
from that view rather than from client code: transfers consume no budget (BR-D1 → FR-010) and
categories excluded from spend contribute nothing (BR-E3 → FR-010). Re-deriving either in Kotlin
would create a second place for them to be wrong.

The **pace comparison** is not in this view — see research R7 for why it is client-side.

### `finance.v_goal_progress`

`goal_id · user_id · saved_paise · link_count`

`Σ (latest valuation of the linked holding × earmark_bps / 10000)` over live `goal_links`, joined
through `v_latest_valuation`. Integer arithmetic throughout — the division is the last operation and
truncates, so a goal's stated progress can never exceed the value actually linked to it.

A goal with no live links returns `saved_paise = 0, link_count = 0`, which is what lets E4 distinguish
"no funding linked yet" from "0% progress" (FR-020) — the two read identically without the count.

### `finance.v_annual_income`

`user_id · income_paise · expense_paise · months_observed`

Trailing 12 months from `v_month_summary`. `months_observed` is the honesty column: E7 uses it to say
what the rule-of-thumb figure could and could not be computed from (research R3, spec Edge Cases),
rather than annualising two months of data and presenting it as a year.

## Functions and trigger

### `finance.fn_goal_link_earmark_guard()` + trigger `trg_goal_link_earmark`

`BEFORE INSERT OR UPDATE ON finance.goal_links` — rejects the write if the sum of live `earmark_bps`
for that `holding_id`, across every goal owned by the same user, would exceed 10000 (FR-024).

**Why a trigger and not repository validation.** A CHECK constraint cannot see other rows, and a
client-side check has a read-then-write race: two goals earmarking the same holding from two screens
can each read 6000-remaining and each write 6000. The rule that must not be bypassable belongs in the
layer that cannot be bypassed — the same reasoning ADR-0029 applied to `ConsentInterceptor` and Phase
3 applied to its audit trigger. The repository still surfaces a readable refusal; the trigger is what
makes the refusal true.

### `public.delete_my_data()` — extended

Extended to hard-delete the six new tables, in FK order: `goal_links` → `goals`, `policy_premiums` →
`policies`, `budgets`, `retirement_scenarios`. Erasure stays exclusively in this function and
`delete_my_account()` (ADR-0029 §5) — no client DELETE policy exists on any of these tables except
`goal_links` (an annotation, not a record).

The function stays in `public` because it spans every app's tracker data (ADR-0033 decision 3); it
references `finance.*` fully-qualified, as it already does for `holdings`/`valuations`.

## State transitions

Only two entities in this feature have a lifecycle worth naming; everything else is created, edited
and soft-deleted.

**Goal**

```
created (no links)  →  funded (≥1 live link)  →  on track | short   [derived, never stored]
                    ↘  unfunded  ←  last link removed
```

`on track` versus `short` is recomputed on every read from `v_goal_progress` against `target_paise`
and `target_date` — there is no status column, because a status column would go stale the moment a
linked holding's valuation moved (FR-017).

**Policy**

```
active  →  renewing (renews_on inside the window)  →  active     [premium marked paid, FR-039]
                                                   ↘  lapsed     (renews_on passed, no payment)
```

Also derived, not stored. Marking a premium paid appends to `policy_premiums`; the banner clears
because the derived state changed, not because a flag was flipped (`INS-FLOW-001`).
